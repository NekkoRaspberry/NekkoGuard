# 1. PRODUCT OVERVIEW

## 1.1 What is NeekoGuard?

NeekoGuard is a self-hosted infrastructure monitoring, network visibility, and security management platform.

Its purpose is to provide a centralized interface where organizations can monitor, understand, and manage their IT infrastructure, local networks, connected devices, services, software, containers, and security exposure.

The initial deployment is intended for a private/home organization using a Raspberry Pi and a local network. However, the platform must be designed to support multiple organizations and multiple clients within each organization.

NeekoGuard combines network discovery, infrastructure inventory, security analysis, monitoring, and operational management into one platform.

The platform should allow users to answer questions such as:

- What devices are connected to my network?
- Which devices are currently online?
- What services and ports are exposed?
- What software is installed on each device?
- Which devices have known vulnerabilities?
- Which certificates are expiring?
- Which containers are running?
- What is happening in my DNS network?
- Have new or unknown devices appeared?
- Has something changed in my infrastructure?
- Are my monitoring agents working correctly?

## 1.2 Main product objectives

NeekoGuard must provide:

- Network discovery and visual network topology.
- Centralized device and infrastructure inventory.
- Port and service monitoring.
- Software and package inventory.
- Vulnerability identification and tracking.
- SSL/TLS certificate monitoring.
- Email and domain exposure monitoring.
- Pi-hole analytics.
- Docker and container management.
- Infrastructure and security event monitoring.
- Agent and collector management.
- Notifications and alerts.
- Historical information and analytics.
- Multi-organization and multi-client management.

The platform should prioritize visibility, security, usability, and clear presentation of technical information.

# 2. PLATFORM STRUCTURE AND MULTI-TENANCY

## 2.1 Organizational hierarchy

NeekoGuard must support multiple organizations.

Each organization may manage multiple clients, sites, networks, and devices.

The logical hierarchy is:

Platform  
└── Organization  
&nbsp;&nbsp;&nbsp;&nbsp;└── Client  
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;└── Site  
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;└── Network  
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;└── Devices

### Organization

An organization represents a tenant using NeekoGuard.

It owns its users, clients, sites, networks, devices, monitoring configuration, integrations, and security findings.

### Client

A client represents a customer, business unit, household, or managed environment belonging to an organization.

An organization can have multiple clients.

### Site

A site represents a physical or logical location belonging to a client.

Examples include:

- Home network.
- Office.
- Data center.
- Remote location.
- Branch office.

### Network

A site may contain multiple networks or subnets.

Each network must have its own discovery configuration and associated devices.

## 2.2 Multiple organizations

Users may belong to multiple organizations.

The application must provide an organization selector that allows users to switch between organizations they are authorized to access.

When switching organizations, all relevant data and pages must reflect the selected organization.

Organization data must remain completely isolated.

## 2.3 User roles

The platform should support these roles:

**Platform Administrator**
- Manages the platform.
- Creates and manages organizations.
- Has platform-level configuration permissions.

**Organization Owner**
- Manages an organization.
- Manages organization users and clients.
- Controls organization settings.

**Organization Administrator**
- Manages organization resources.
- Manages users and permissions.
- Configures monitoring and integrations.

**Security Analyst**
- Reviews devices, vulnerabilities, exposed services, certificates, and alerts.

**Operator**
- Performs authorized operational actions, including permitted container operations.

**Viewer**
- Has read-only access to authorized information.

Permissions must always be validated by the backend.

# 3. AUTHENTICATION AND ACCOUNT SECURITY

NeekoGuard must provide secure user authentication.

Required functionality:

- Login using email and password.
- Multi-factor authentication (MFA).
- TOTP authenticator application support.
- Recovery codes.
- Password reset.
- Session management.
- Logout.
- Protection against repeated login attempts.
- User profile management.

MFA must be available to users and should be required according to the platform's security policy.

The interface must clearly communicate whether MFA is enabled and provide an understandable enrollment and recovery experience.

Recovery codes must be treated as sensitive information and must not be exposed again after their initial issuance.

# 6. NETWORK DISCOVERY & TOPOLOGY

## 6.1 Purpose

Network Discovery & Topology is one of the most important features of NeekoGuard.

It provides a visual representation of the monitored network and allows users to understand which devices exist, their status, their network location, and their known relationships.

The feature must combine:

1. A graphical network topology.
2. A structured device list.
3. Device details.
4. Discovery controls.
5. Network filtering.
6. Discovery history.

## 6.2 Mandatory visual references: Images 1, 2 and 3

The three Network Discovery & Topology reference images previously supplied by the product owner are the mandatory visual references for this page.

They must guide the final frontend design.

The intended result is not a generic network diagram. The actual layout, visual hierarchy, colors, spacing, node presentation, controls, and panel arrangement must follow the three supplied images.

The reference images take priority over generic design assumptions.

The required functionality in this section must be integrated into that visual direction.

**Important:** The original image files are not embedded in this text document. Their exact visual details must therefore be taken directly from the original images when they are available to the design team. No unrelated images should be substituted for them.

## 6.3 Topology view

The topology view must provide a large graphical workspace showing discovered network devices.

Devices must be represented as nodes.

Known relationships between devices must be represented as connecting lines or edges.

The topology must support:

- Zoom in.
- Zoom out.
- Pan.
- Fit the complete network into the visible area.
- Select individual devices.
- Search for devices.
- Filter devices.
- Group devices logically.
- Display device status.
- Display device labels.
- Refresh the displayed information.

The topology should remain understandable when many devices are present.

Device labels must remain readable, and the graph should avoid unnecessary overlap.

## 6.4 Device representation

Each device node should communicate its identity and relevant status.

Where available, device information should include:

- Hostname.
- IP address.
- MAC address.
- Manufacturer/vendor.
- Device category.
- Operating system.
- Online/offline status.

Different device categories should be recognizable.

Examples include:

- Router.
- Switch.
- Server.
- Workstation.
- Laptop.
- Mobile device.
- Raspberry Pi.
- IoT device.
- Printer.
- Unknown device.

The application must not invent a device category when the available information is insufficient.

## 6.5 Device selection

When a user selects a device, the interface must show its relevant information.

This may be displayed in a contextual information panel or a dedicated detail view, following the visual arrangement of the supplied references.

The information should include:

- Device identity.
- Current status.
- IP and MAC addresses.
- Network and subnet.
- Vendor and device type.
- First discovery.
- Last seen.
- Detected services.
- Open ports.
- Installed software, when available.
- Vulnerabilities, when available.
- Certificates, when associated.
- Historical changes.

The user must be able to navigate from the selected device to its full device detail page.

## 6.6 Network filtering

Users must be able to filter the topology by:

- Organization.
- Client.
- Site.
- Network.
- Subnet.
- Device type.
- Online/offline status.
- Device name.
- IP address.
- MAC address.

Filters must be visible and understandable.

Users must be able to clear filters and return to the complete network view.

## 6.7 Topology and list views

The page must provide both graphical and structured representations.

**Topology view**

Used to understand the network visually and inspect relationships.

**List view**

Used to search, sort, filter, and review device information in a structured format.

Both views must represent the same underlying device inventory.

Switching views should preserve the current network scope and relevant filters whenever possible.

## 6.8 Discovery process

The system must allow authorized users to configure and initiate network discovery.

Users should be able to define:

- Network or subnet.
- Discovery scope.
- Associated site.
- Associated client.
- Discovery settings permitted by their role.

Discovery must only target explicitly authorized networks.

The interface must show:

- Discovery status.
- Start time.
- Completion time.
- Devices discovered.
- Discovery errors.
- Last successful discovery.

## 6.9 Device history

NeekoGuard must retain discovery history.

It should record:

- New devices.
- Devices no longer detected.
- Online/offline transitions.
- IP address changes.
- Hostname changes.
- Vendor or device information changes.
- Newly detected services.
- Changes to previously observed services.

This history must be accessible from the device and relevant network views.

## 6.10 Relationship accuracy

The topology must distinguish observed relationships from inferred relationships.

For example, devices sharing the same subnet must not automatically be represented as physically connected to each other.

The application must not claim to know physical switch ports, cables, or network paths unless that information is actually available.

## 6.11 Visual requirements

The topology page must follow the three original reference images.

The page must preserve a clear hierarchy between:

- The main topology workspace.
- Network and discovery controls.
- Filters.
- Selected-device information.
- Discovery status.

Status colors should be consistent and meaningful.

The topology must be the main working area, not merely a decorative element above a device table.

The page should feel like a dedicated network operations interface.

# 20. FRONTEND VISUAL DESIGN

## 20.1 Overall visual direction

The frontend should have a professional infrastructure and security operations appearance.

The design should prioritize:

- A clear and consistent navigation system.
- Structured information.
- Readable technical data.
- Consistent spacing.
- Clear page titles and context.
- Compact operational dashboards.
- Well-organized tables.
- Contextual detail panels.
- Meaningful status indicators.

Avoid unnecessary decorative images, generic illustrations, and oversized visual elements that reduce the available space for useful information.

## 20.2 Consistency across pages

All sections must share the same visual language.

The Network Discovery & Topology page's three supplied reference images are the primary visual reference for that page.

The remaining pages should feel like parts of the same application, using consistent navigation, typography, spacing, panels, tables, filters, and status treatments.

## 20.3 Tables

Tables should be easy to scan and should support relevant sorting, filtering, and pagination.

Important identifying fields should be visible without requiring users to open every row.

Technical values such as IP addresses, ports, package versions, and certificate fingerprints should be presented clearly.

## 20.4 Detail panels

Related information should be grouped into logical sections.

Where possible, users should be able to move between related devices, services, vulnerabilities, certificates, and events.

## 20.5 Status indicators

Status colors must have consistent meanings throughout the application.

Color must not be the only way to communicate status. Use text labels or icons alongside colors.

Critical findings should be prominent without making the entire interface visually overwhelming.

## 20.6 Charts

Charts should communicate useful information.

They should include appropriate labels, time ranges, legends, and units.

Avoid charts that are purely decorative or do not answer an operational question.

## 20.7 Responsive behavior

The application should be usable on desktop and tablet screens.

The topology and dense operational tables may prioritize desktop presentation, but narrower screens must still provide access to the relevant information through appropriate resizing, scrolling, or alternate layouts.

## 20.8 Frontend technology requirement

The frontend must use:

**React with TypeScript.**

TypeScript is mandatory for frontend application code.

Plain JavaScript must not be used as the frontend application language.

# 21. DEPLOYMENT CONFIGURATIONS

NeekoGuard must support three deployment configurations.

These are three ways to deploy the same product, not three different products.

## 21.1 Local Raspberry Pi deployment

Intended for the initial self-hosted environment.

Requirements:

- Runs within the user's local infrastructure.
- Supports monitoring of the local network.
- Supports local access.
- Supports the required agent and integrations.
- Provides the same core product experience.

## 21.2 Development deployment

Intended for development and testing.

Requirements:

- Runs in its own isolated containerized environment.
- Uses separate configuration and data.
- Does not interfere with local or production environments.

## 21.3 Production deployment

Intended for stable and secured operation.

Requirements:

- Secure access.
- Encrypted communication.
- Protected secrets.
- Controlled permissions.
- Operational visibility.
- Separation from development and local environments.

# 22. SECURITY & PRIVACY REQUIREMENTS

Security is a fundamental product requirement.

NeekoGuard must provide:

- Backend authorization for every protected operation.
- Strict organization and client data isolation.
- Encrypted authenticated communication.
- Secure handling of passwords and tokens.
- Secure handling of agent credentials.
- Protection of integration credentials.
- Least-privilege permissions.
- Audit history for important actions.
- Revocation of agent credentials.
- Authorized discovery scopes.
- Confirmation for disruptive operations.
- Protection against sensitive information appearing in logs.
