Conventions used in this document

DELIVERABLE 1 — EXISTING PROJECT ANALYSIS
=====================================================================================================

1.1 Repository layout (as found)

  NekkoGuard/
  ├── README.md, .gitignore
  ├── Specifications/                 (untracked) product spec + 5 reference images + this file
  └── nekkoguard/                     Django project generated with cookiecutter-django
      ├── config/                     settings (base/local/production/test), urls, api_router, asgi, celery_app, websocket
      ├── nekkoguard/

      │   ├── templates/              Bootstrap 5.2 server-rendered templates (base, home, about, allauth, users)
      │   └── static/                 project.css (13 lines), project.js (empty), favicon
      ├── compose/                    Dockerfiles for django, celery worker/beat/flower, postgres, traefik, nginx, docs
      ├── docker-compose.{local,development,production,docs}.yml
      └── pyproject.toml / uv.lock    Python dependencies (managed with uv)

1.2 Backend technologies (confirmed in code)
  - Django 6.0, Python (uv), PostgreSQL, Redis, Celery 5.7 + celery-beat + Flower.
  - Django REST Framework, authentication = Session + Token, default permission = IsAuthenticated.
  - drf-spectacular: OpenAPI schema at /api/schema/, Swagger UI at /api/docs/.
  - django-allauth with the MFA extension (allauth.mfa) → TOTP + recovery codes are available server-side.
  - django-cors-headers installed.
  - ASGI entrypoint + websocket.py stub (ready for live updates later; no real channels yet).
  - Traefik + nginx in production compose.

1.3 Frontend technologies (confirmed in code)
  - Only Django templates + Bootstrap 5.2 from CDN. No React, no TypeScript, no package.json, no bundler.
  - Node.js is NOT installed on the Raspberry Pi host (checked: `node` not found).

1.4 Existing API surface
  - /api/users/ (UserViewSet: list/retrieve/me), /api/auth-token/, /api/schema/, /api/docs/.
  - Nothing else. No models or endpoints exist for organizations, clients, sites, networks, devices,
    ports, software, vulnerabilities, certificates, domains, Pi-hole, containers, logs, agents, alerts,
    analytics or settings.

1.5 Hard requirements that affect the frontend
  - [SPEC 20.8] React + TypeScript is mandatory. Plain JavaScript must not be used for app code.
  - [SPEC 2] Multi-tenant: Platform → Organization → Client → Site → Network → Devices; org selector required.
  - [SPEC 2.3] Six roles; permissions always validated by backend (frontend only hides/disables).
  - [SPEC 3] Email+password login, MFA (TOTP), recovery codes shown once, reset, sessions, logout, profile.
  - [SPEC 4.2] 15 navigation sections (listed in Deliverable 4).
  - [SPEC 4.4] Global search across hostnames, IPs, MACs, devices, services, ports, packages, CVEs, certs, containers, events.
  - [SPEC 20.7] Desktop + tablet. Topology and dense tables may prioritise desktop.
  - [SPEC 23] Unknown ≠ healthy, stale data visibly distinguished, freshness visible, empty states explain why,
    disruptive actions confirmed.

1.6 Host constraints (from CLAUDE.md, NekkoRaspberry rules)
  - Raspberry Pi 4 / 8 GB, SD card: minimise writes, keep build/runtime light.
  - Docker-first: the frontend build should run inside a container (node image, ARM64), not on the host.
  - The built SPA is static files → served by nginx/Django; no Node process needed at runtime.

1.7 Consequence
  The frontend has to be built from zero, and almost every screen depends on backend models/APIs that do not
  exist yet. Any implementation done now must use a clearly separated mock layer (see 8.6) and must never
  present mock data as real integration.

2.A  Assets.jfif — ASSET / NETWORK DISCOVERY  (primary reference for Network Discovery & Topology)
-----------------------------------------------------------------------------------------------------
What it shows
  A three-column operations screen on a near-black background:
  1. Thin icon rail (far left, ~80px) → section switching.
  2. Left list panel (~30%): back-arrow + "Network" title, a summary card for the current network
     (name, online state, active device count, last update), a "Devices" section with a search input,
     quick filter chips ("High Risk", "Last Scan"), and a vertical list of device cards
     (category icon coloured by state, name + address, state + connection count, time-ago on the right).
     The selected card has a bright 1px white outline.
  3. Centre "Network Map" canvas (~45%): title + subtitle, fit-to-screen button top-right, minimap
     top-right, a subtle dotted/grid background. Nodes are SQUARE-ish dark cards with a 1px border,
     a coloured category icon on top, bold name, muted address, and a small issue counter.
     Edges are thin grey lines; a highlighted path is green; the edge from the selected node to a
     problem node is red. Small square "badges" sit on the midpoint of edges (lock icon, scan icon).
     The selected node has a white border and a soft RED radial glow behind it.
  4. Right "Device details" panel (~25%): close (X) button, device name + category icon + status pill,
     a 2×2 key/value grid (IP/CIDR with "copy" tooltip, device type, last scan, score), a full-width
     outlined primary action, then sections with icon headers: Relationships (list of related devices
     with their link reason), Security & Health (rows with chevrons that drill down), Activity Timeline
     (time-stamped events).

What to adopt (and why)
  - The 3-zone layout (list ↔ canvas ↔ details) keeps the graph as the main workspace while giving
    structured access to the same inventory. This matches [SPEC 6.1, 6.7, 6.11] exactly.
  - Card-style square nodes with icon+name+address: far more legible than circles with floating labels,
    and labels never collide with edges. Satisfies [SPEC 6.3] "labels must remain readable".
  - Colour used ONLY for meaning: green = healthy/online, red = problem; everything else is grey.
    The calm grey canvas makes a single red glow instantly findable.
  - Selection = outline + glow + highlighted incident edges; non-related nodes stay normal (no heavy dimming).
  - Minimap + fit button → orientation in large networks.
  - Detail panel organised in titled sections with drill-down rows ("3 Detected Issues ›") → progressive
    disclosure instead of dumping all data.
  - Copy-to-clipboard on technical values (IP/MAC).
  - Monospace-friendly, compact typography for addresses.

What NOT to adopt (not in the spec)
  - "Risk Score" / "Threat Level" gauges — no risk scoring is defined in the spec. [OPEN Q7]
  - "Analyse Path" action — the spec forbids claiming network paths that are not known [SPEC 6.10].
  - Lock icons on edges (encryption state of a link) — no such data in the spec.
  - "NOVA" AI assistant, purple toast, mascot — not in the spec.
  - "Connections" count per device — only if observed relationships exist; otherwise omit.

2.B  Vulnerabilities.jfif — VULNERABILITIES
-----------------------------------------------------------------------------------------------------
What it shows
  Near-black app frame, minimal text sidebar (Dashboard, Assets, Vulnerabilities, Changes, Reports) with
  a soft purple gradient pill for the active item. Page title left, period selector + purple primary
  button right. Row of 3 KPI cards (icon + label, very large number, delta chip, small sparkline).
  Main card "Common vulnerabilities found": a table with only three columns — a square SEVERITY SCORE
  tile (red ≥9, orange 7–9), a two-line CVE cell (human title on line 1, CVE id in a small outlined
  monospace chip on line 2), and a small status chip on the right. Hovered row has a slightly lighter
  background. A second card shows a world map + region bars.

What to adopt (and why)
  - Very few columns in the main list; detail lives in a side panel. Readability over density.
  - Severity as a square numeric tile with tinted background + coloured border: scannable, works for
    colour-blind users because the number is always visible ([SPEC 20.5]).
  - Two-line cell: readable title first, identifier as a quiet monospace chip.
  - Small, muted status chips (not loud pills).
  - KPI cards with one number + one context line.
  - Generous row height (~52px) and consistent left alignment.

What NOT to adopt
  - World map / "Compromised assets by region" — no geolocation in the spec.
  - "Total exploits" — spec only has "known-exploited status, when supported by a trusted source" →
    shown as a badge per finding, optionally a KPI if the backend provides it.
  - "Download report" — no export defined in the spec. [OPEN Q9]
  - Week-over-week delta % — only if analytics history provides it; never fabricate. [SPEC 18]

DELIVERABLE 3 — UNIFIED VISUAL DIRECTION
=====================================================================================================

Name of the direction: "Night Console"
  A dark, layered, violet-tinted operations console. Calm grey/graphite surfaces, violet for interaction,
  a strict semantic status palette (green / amber / orange / red / blue / grey) for meaning only.

How the references merge
  ┌───────────────────────┬─────────────────────────────────────────────────────────────────────┐
  │ From Colors + navbar  │ Global shell, surface layers, violet interaction colour, pills,       │
  │                       │ grouped sidebar, page header with freshness + refresh.                │
  │ From Assets           │ The 3-zone workspace pattern (list | canvas | detail panel), square    │
  │                       │ card nodes, grid canvas, minimap, red/green-only meaning, detail       │
  │                       │ sections with drill-down rows, copy-to-clipboard. Reused for ALL       │
  │                       │ "inspect a record" interactions (right detail panel).                  │
  │ From Vulnerabilities  │ The default TABLE style for every list page: few columns, two-line     │
  │                       │ cells, square severity tile, quiet chips, generous rows, KPI strip.    │
  │ From Logs             │ The DENSE variant of the table (32px rows, monospace timestamps), the  │
  │                       │ left summary rail with coloured markers, card headers with icon +      │
  │                       │ title + segmented tabs, chart cards.                                   │
  └───────────────────────┴─────────────────────────────────────────────────────────────────────┘

The Assets reference is pure neutral black/graphite; the Colors reference is violet-navy. The unified
palette uses a graphite base with a very slight violet tint (hue ~250°) so both feel native: the
topology canvas stays almost neutral (the colours of nodes must dominate), while the shell carries the
violet identity.

Principles
  1. Colour = meaning. Only status/severity colours and the single violet accent. No decorative colour.
  2. Depth by surface lightness + hairline borders first, shadow second (only for floating layers).
  3. One record inspector pattern: a right-side detail panel (480px) everywhere; full pages only for
     Device detail and Container detail ([SPEC 7.3, 14.4] require dedicated pages).
  4. Two table densities: "comfortable" (52px, Vulnerabilities style) and "compact" (36px, Logs/Ports style).
  5. Unknown / stale / unavailable have their own neutral visual treatment — never green [SPEC 5.2, 23.7-8].
  6. Radius small (6px controls, 10px cards, 14px shell container). Not pill-everything.
  7. Motion: 120–200ms ease-out for hovers/panels; no decorative animation. Respect prefers-reduced-motion.
  8. Dark theme is the primary and only theme in v1 [DESIGN] (light theme = [OPEN Q11]).

  Sidebar groups [DESIGN — grouping allowed by SPEC 4.2]
    MONITOR      Overview · Network Discovery & Topology · Devices
    EXPOSURE     Ports & Services · Software Inventory · Vulnerabilities · Certificates · Email & Domain Exposure
    OPERATIONS   Pi-hole · Containers · Logs · Agents
    RESPONSE     Alerts · Analytics & Reports
    (bottom)     Settings
    footer       Agent health summary: "● 3 agents online · 1 unavailable" (links to /agents)
  - Active item: violet tinted pill + 2px violet left marker + white text. Hover: surface-3 background.
  - Badges: numeric only (open alerts, critical vulns). Hidden when 0 or unknown.
  - Collapsible to a 64px icon rail (tooltip on hover); collapsed state remembered in localStorage.
  - Items the role cannot access are hidden; backend still enforces [SPEC 2.3].

  Context selector [SPEC 2.2, 4.3]
  - Breadcrumb-style chained dropdowns: Organization → Client → Site → Network. Client/Site/Network have an
    "All" option. The organization is always visible and never "All".
  - Changing the organization: clears selected client/site/network, invalidates ALL cached data
    (TanStack Query cache cleared), navigates to the same module root, shows a toast "Switched to <Org>".
  - Context is stored in the URL (?org=&client=&site=&network=) + localStorage default.

  Global search [SPEC 4.4]
  - Input in top bar, opens a command-palette modal (Ctrl/⌘+K).
  - Results grouped by type: Devices, Services/Ports, Software, Vulnerabilities, Certificates, Containers,
    Events. Each result: type icon, primary text, monospace secondary (IP / MAC / CVE / fingerprint),
    context (client/site). Enter → opens the record. Results scoped to current org, filtered by backend.
  - States: typing (<2 chars: recent searches), loading skeleton rows, "No results in <Org>", error inline.

  Page header
  - Title (H1), purpose line (muted), freshness ("Updated 2 min ago", amber "Stale — last update 3 h ago"
    when older than the module's freshness threshold [OPEN Q12]), Refresh button, primary action(s).

  Shell states
  - Session expired → redirect to /login?next=…
  - 403 for a module → in-page "You don't have access to <Module> in <Org>" (no data leaked).
  - Backend unreachable → top banner (danger) "Cannot reach NekkoGuard server. Retrying…".

  Responsive
  - 1280+: full layout. 1024–1279: sidebar collapsed to icon rail. 768–1023 (tablet): sidebar becomes an
    overlay drawer; context selector collapses into one "Context" button; detail panels become full-width
    sheets. <768: supported read-only best effort (stacked), not optimised [SPEC 20.7].

4.2 Standard page anatomy and shared states

  List page template ("Registry" layout — Vulnerabilities style)
    Page header → optional KPI strip (3–5 cards) → Filter bar → Table card → right Detail panel on row click.
  Filter bar: search input (left), filter dropdown chips, active-filter chips with ×, "Clear all",
    result count ("245 findings"), density toggle, column picker.
  Table: sticky header, sortable columns, row hover, row click → panel, keyboard ↑/↓ + Enter,
    server-side pagination (25/50/100), technical values in monospace with copy-on-hover.

  Loading: skeleton rows/cards matching final layout (no spinner-only pages). Inline spinner on Refresh.
  Empty: icon + one sentence explaining WHY + next step, e.g. "No devices discovered in Home network yet.
    Run a discovery to populate the inventory. [Start discovery]" (action only if role permits) [SPEC 23.12].
    Separate copy for "no results for these filters" → [Clear filters].
  Error: card with danger icon, the backend error message (sanitised), request id if provided, [Retry].
  Unknown values: rendered as "Unknown" in text-muted italic — never blank, never "0" [SPEC 23.7, 18].
  Stale data: amber "Stale" chip next to freshness timestamp + tooltip with last successful update.
  Unavailable integration: neutral grey card "Pi-hole integration unavailable since <time>" + link to Settings.

4.3 Authentication & account pages [SPEC 3]

  Purpose: secure access, MFA enrolment and recovery, session control, profile.
  Layout: "entrance" layout — centred 400px card on the background, product logo above, no sidebar.
  Pages
  - Login: email, password, "Forgot password?", submit. Errors: invalid credentials (generic message),
    rate-limit lock "Too many attempts. Try again in N minutes." (from backend).
  - MFA challenge: 6-digit TOTP input (auto-advance, paste support) + "Use a recovery code" link.
  - Password reset request / confirm: email form → generic confirmation ("If an account exists…").
  - Account › Profile: name, email (read-only or change flow per backend), save.
  - Account › Security: MFA status card ("MFA enabled" green pill / "MFA not enabled" amber pill +
    "Required by your organization" when policy enforces it). Enrolment wizard: 1) scan QR + manual key,
    2) confirm code, 3) recovery codes shown ONCE with Copy / Download .txt and a mandatory checkbox
    "I have stored these codes" before closing. Afterwards only "Regenerate recovery codes" (with
    confirmation) — codes are never re-displayed [SPEC 3].
  - Account › Sessions: table (device/browser, IP shown as returned by backend, last activity, current
    session badge), "Sign out" per session, "Sign out all other sessions" (confirm).
  - Logout: user menu → immediate logout → /login.
  Backend dependency: allauth headless API or custom endpoints [OPEN Q3].

4.4 Overview [SPEC 5]

  Purpose: environment state at a glance; every element links to its detailed page.
  Layout (12-column grid)
    Row 1 — KPI strip (6 compact cards): Devices (total · online · offline), Networks monitored,
            Agents (active · unavailable), Open vulnerabilities (critical · high), Expiring certificates,
            Containers (running · stopped).
    Row 2 — left 8 cols: "Network activity" chart card (Pi-hole DNS queries vs blocked over time, tabs
            24h/7d/30d). right 4 cols: "Security" stack — newly discovered devices, newly exposed ports,
            recent security alerts (Logs-style stack with coloured left markers + View links).
    Row 3 — left 6 cols: "Services" — detected open ports count, important service changes list,
            Docker host status list. right 6 cols: "Recent activity" timeline (new devices, status changes,
            new vulns, certificate changes, agent connection changes, container events) with type icon,
            time, link.
  States: each card loads/errors independently. A card whose source is unavailable shows the grey
  "Unavailable" treatment — not zero, not green [SPEC 5.2]. Health summary uses 5 states:
  healthy, warning, critical, unavailable, unknown.
  Interactions: click any KPI → module with matching filter applied (e.g. Vulnerabilities?severity=critical,high&status=open).

4.5 Network Discovery & Topology [SPEC 6] → full detail in Deliverable 5.

  Sub-pages
  - Topology (default) and List view (toggle; same data, same filters) [SPEC 6.7].
  - Discovery: discovery configurations per network (subnet, scope, site, client, role-permitted settings),

4.6 Devices [SPEC 7]

  Inventory page (Registry layout, comfortable density)
  - Columns: Device (category icon + name, 2nd line hostname) · IP · MAC · Type · Manufacturer · Client ·
    Site · Network · Status pill · Last seen (relative, absolute in tooltip).
  - Flags column icons: managed / ignored / under investigation; labels as small chips.
  - Filters: search (name/IP/MAC), type, status, client, site, network, group, flag.
  - Bulk select → assign group / mark managed / ignored / investigate (role-gated).
  - Row click → opens Device detail page (not panel — spec requires a dedicated page).

  Device detail page (/devices/:id/:tab)
  - Breadcrumb: Devices › <name>. Header card: category icon, name, status pill, IP/MAC (copy), vendor,
    OS, client/site/network, first discovered, last seen, freshness. Actions: Edit labels/notes, Group,
    Mark managed / ignored / investigate, "Show in topology".
  - Tabs (URL-addressable): Overview · Network · Ports & Services · Software · Vulnerabilities ·
    Certificates · Containers · Logs & Events · History. Each tab reuses the module's table component
    pre-filtered by device (no duplicate implementations).
  - Manual vs discovered data: manually entered fields carry a small "Manual" chip + pencil icon and a
    tooltip "Entered by <user> on <date>"; discovered fields carry "Discovered" source tooltip [SPEC 7.4].
  - Notes: markdown-free plain text area with author/time list.

4.7 Ports & Services [SPEC 8]

  Layout: Registry, compact density (port data is dense).
  - KPI strip: open ports, new in last 24h, no longer available (24h), services with uncertain identification.
  - Columns: Device · IP · Port (monospace, right-aligned) · Protocol (TCP/UDP chip) · Service ·
    Version · Confidence (Confirmed ✓ / Uncertain ? chip) · Detected · Status (Open / Closed / New / Gone).
  - Tabs: Current | Changes (timeline of opened/closed/changed services).
  - Filters: device, network, port, protocol, service, status, confidence.
  - Detail panel: port/service facts, evidence, history sparkline (open/closed over time), links to
    device, related certificate (if TLS), related vulnerabilities.
  - "Uncertain" identification uses dashed-border chip + "?" icon, never the same as confirmed [SPEC 8.3].

5.12 Technology choice and implementation approach
  Options evaluated
    a) React Flow (@xyflow/react, MIT) — nodes are React components → the card-style nodes, counters,
       badges, hover/selection states are plain JSX + CSS tokens. Built-in pan/zoom, MiniMap, Controls,
       Background (dot grid), group/sub-flow nodes, viewport fitting. Good to ~1–2k nodes with LOD.
    b) Cytoscape.js — strong graph algorithms and canvas rendering for very large graphs, but nodes are
       canvas-drawn → the card UI from the reference is hard to reproduce; styling separate from CSS tokens.
    c) D3-force hand-built — maximum control, much more code, force layouts are non-deterministic
       and overlap labels (violates "avoid unnecessary overlap").
    d) Sigma.js / WebGL — for 10k+ nodes; overkill for a home/SMB network.
  Recommendation: (a) React Flow + elkjs for layout.
    - elkjs "layered" algorithm with compound nodes gives deterministic hierarchical layout with subnet groups.
      Run it in a Web Worker (elkjs ships a worker build) so layout never blocks the UI.
    - Both are lazy-loaded only on the /network route (code splitting) — keeps the rest of the app light.
    - Custom node types: DeviceNode, GroupNode, CollapsedGroupNode. Custom edge: RelationEdge (observed/inferred).
    - Graph data → transformed in a pure function `toFlowGraph(devices, relations, grouping, filters)` that is
      unit-tested; React Flow only renders.
  Performance rules: memoised node components, `onlyRenderVisibleElements`, LOD by zoom, no shadows on
  nodes at low zoom, virtualised left list.

7.4 Mock data policy (because backend APIs do not exist)
  - Mocks live ONLY in src/api/mocks/ and are served via MSW (Mock Service Worker) at the HTTP level, enabled
    only when VITE_USE_MOCKS=true in development. Production builds exclude them.
  - When mocks are active a persistent violet banner shows "Demo data — not connected to backend".
  - Mock data uses placeholder addresses from documentation ranges, never real home-network values.
  - Every mocked endpoint is listed in an "API contract needed" table that becomes the backend backlog.

7.5 Type conventions
  - `type Maybe<T> = T | null` for "unknown" values from backend; UI renders null as "Unknown" via a shared
    <Value> component. Never coerce unknown to 0/false.
  - Status unions as string literal types (e.g. `type DeviceStatus = 'online' | 'offline' | 'unknown'`) with
    exhaustive mapping in statusMap.ts.
